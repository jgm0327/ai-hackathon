# 푸시 알림 아키텍처 (Track E — 선택 기능)

## 결론부터
"퇴근 15분 전 알림"은 구현 난이도가 크게 다른 두 단계로 나뉜다. 해커톤 일정상
**Tier 1을 기본으로 하고, Tier 2는 시간이 남을 때만 시도**하는 것을 권장한다.

## Tier 1 — 탭이 열려 있는 동안만 동작 (권장, 저비용)
- 브라우저 `Notification` API를 JS로 직접 호출. Service Worker 불필요.
- 유저가 퇴근 시각을 입력하면, 프론트엔드에서 "현재 시각 ~ (퇴근시각-15분)" 차이를
  계산해 `setTimeout`을 걸어두고, 시간이 되면 브라우저 알림을 띄운다.
- **제약**: 탭을 닫거나 브라우저를 종료하면 타이머가 사라져서 알림이 안 온다.
  데모/개인 사용(항상 탭을 켜놓고 씀) 수준에서는 충분하지만 "진짜 서비스"로는 약하다.
- 구현 위치: `src/frontend/components/reminder.py`

## Tier 2 — 탭/브라우저를 꺼도 동작 (Web Push, 고비용)
이게 되려면 3가지 요소가 모두 필요하다.

1. **PWA 등록**: `static/manifest.json` + `static/service-worker.js`
   서비스워커가 백그라운드에서 push 이벤트를 받아 OS 알림을 띄운다.
2. **구독(subscription) 저장**: 유저가 알림을 허용하면 브라우저가 발급하는
   `PushSubscription` 객체(엔드포인트 URL + 암호화 키)를 서버에 저장해둬야 한다.
   → `src/push/subscription_store.py`
3. **정해진 시각에 서버가 능동적으로 푸시를 쏘는 트리거**: 이게 가장 까다로운 부분이다.
   Streamlit 앱은 유저가 탭을 열어야만 코드가 돌아가는 구조라, "매일 정해진 시각에
   알아서 실행되는 백그라운드 작업"을 Streamlit 안에서 안정적으로 돌리기 어렵다.
   (Streamlit Cloud는 무료 티어에서 일정 시간 미사용 시 앱이 슬립 상태로 전환될 수 있음)

   **트리거 옵션 (택1)**:
   - **GitHub Actions 스케줄 워크플로**: `cron` 문법으로 원하는 시각마다
     별도의 작은 엔드포인트(또는 스크립트)를 실행해서 저장된 구독 목록에 푸시 발송.
     추가 인프라 없이 GitHub 저장소만으로 가능해서 해커톤 규모에 가장 현실적.
   - **외부 무료 cron 서비스** (예: cron-job.org): 지정 URL을 주기적으로 호출.
     단, 그 URL을 받아서 실제로 푸시를 발송하는 엔드포인트가 필요하므로 별도의
     경량 백엔드(Flask/FastAPI, Render/Railway 무료 티어 등)가 하나 더 필요.
   - **APScheduler를 상시 실행 프로세스로**: 로컬 데모에는 되지만, Streamlit Cloud
     같은 서버리스형 호스팅에서는 프로세스가 계속 살아있다는 보장이 없어 신뢰하기 어렵다.

   → 해커톤 기간 안에는 **GitHub Actions 스케줄 워크플로**가 추가 인프라 없이 가장
   빠르게 구현 가능하다.

## 권장 결론
- 데모/제출용 MVP: **Tier 1만 구현**해도 "알림 기능이 있다"는 걸 보여주기에 충분함
- 시간이 남고 완성도를 더 높이고 싶다면: Tier 2를 GitHub Actions 트리거 방식으로 추가
- Tier 2를 붙이기로 했다면 반드시 `tasks/track-e-push-notifications.md`의 타임박스를
  지킬 것 (다른 트랙처럼 무한정 투입하지 않기)
